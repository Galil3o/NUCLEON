# Nucleon v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the headless Nucleon engine that reads Proton mail (read-only), classifies it with a quarantined model, auto-applies reversible labels, optionally moves mail to Trash (opt-in cleanup), and stages reply drafts for native human sending — with an opt-in metadata-only journal whose storage location the operator chooses.

**Architecture:** A deterministic core orchestrates four seams behind interfaces — `MailStore` (mail access), `Classifier` (quarantined model), `gate` (policy), `Journal` (audit, over a pluggable `JournalStore`) — so the whole pipeline is tested against in-memory fakes with no live mailbox or model. Real adapters (`ImapMailStore`, `LLMClassifier`) are thin and unit-tested with stubs; their live acceptance against a real Bridge/model is a post-v0.1 gate.

**Tech Stack:** Python ≥ 3.11, `pydantic` (models/config), `PyYAML` (config), standard library for IMAP/MIME/HTTP/hashing (`imaplib`, `email`, `urllib.request`, `hashlib`). Dev: `pytest`. `src/` layout.

**Spec:** `docs/CONCEPT.md`

## Global Constraints

- Repository language: **English**. License: **Apache-2.0**.
- **No SMTP / no send path** in v0.1 (drafts-only). No `Action` type for send exists.
- **Deletion is move-to-Trash only** (reversible, recoverable) and **opt-in / policy-gated, off by default**. Nucleon never permanently deletes: no untargeted `EXPUNGE`, no emptying of Trash, no permanent-delete action type exists.
- **No raw mail persisted:** anything written to disk or a remote backend (journal, state) holds **metadata and hashes only** — never bodies, subjects, addresses, or attachments.
- **Account-neutral:** the engine holds no account identity, credentials, or data; everything comes from config. `config.example.yaml` contains **placeholders only**.
- **Minimal dependencies:** prefer the standard library; the only runtime deps are `pydantic` and `PyYAML`.
- Draft label is exactly `nucleon/proposed`. Draft staging target is `drafts` (native Drafts) or `outbox` (`Nucleon/Outbox`), from config.
- All Sent access and reconciliation are **read-only**. Body reads use `BODY.PEEK` (flags must not change).

## Review Focus

- **Prompt injection in message content** must not change which actions the gate allows — the gate reads only validated fields, never instruction-like text. → Task 5.
- **Malformed / attacker-shaped model output** (non-JSON, missing or extra fields) is rejected, never executed. → Task 4.
- **Deletion is Trash-only, never permanent, and off unless explicitly enabled** — a classification error or injection can at worst move a message to a recoverable Trash. → Tasks 5, 6, 9.
- **Re-processing a message** must not create a duplicate draft or re-trash (idempotency via journal). → Task 8.
- **Body fetch uses `BODY.PEEK`** and never sets `\Seen` or other flags; no untargeted `EXPUNGE` is ever issued. → Task 9.
- **The journal never persists** bodies, subjects, or addresses — metadata and hashes only, wherever the backend writes. → Task 7.

**Interfaces:**
- Produces:
  - `MessageRef(account_hash, mailbox, uidvalidity: int, uid: int, message_id_hash: str | None, raw_hash: str)` with `@classmethod from_source(account_hash, mailbox, uidvalidity, uid, message_id: str | None, raw: bytes) -> MessageRef` (hashes via `hashlib.sha256`) and `key() -> str` (stable `"{account_hash}:{mailbox}:{uidvalidity}:{uid}"`).

  - `JournalEntry(ref_key: str, account_hash, mailbox, uid: int, message_id_hash, raw_hash, action: Literal["classified","drafted","trashed","marked_sent"], status: str, ts: datetime)` — **no body/subject/address fields.**

## Out of scope for v0.1 (seams left open)

SMTP/sending (the optional-send seam), **permanent** deletion (expunge / emptying Trash), remote journal backends beyond the local file (additional `JournalStore` implementations — private Git repo, cloud drive), a web/API frontend (the frontend seam connects to the engine later), non-Proton providers (additional `MailStore` implementations), and attachment/Drive handling. None require changes to the interfaces defined above.
